# 「筷点吃饭」产品评估报告

> 评估视角：腾讯资深产品经理
> 评估对象：`miniprogram-11`（筷点吃饭 · 家庭就餐决策小程序）
> 评估日期：2026-09-06
> 评估依据：产品设计稿 v1.0、README（v1.2.0+）、13 个前端页面源码、6 个云函数、7 个数据库集合设计、git 提交与迭代验收记录
> 说明：本次未收到界面截图附件，视觉与交互判断基于 WXML/WXSS 源码、主题系统设计文档与素材清单推导

---

## 〇、一句话结论

**这是一个"工程完成度显著高于产品完成度"的项目。**

后端与工程规范已达到可上线标准（契约统一、错误码体系、幂等设计、CI、68 项测试），核心决策闭环（投票 → 汇总 → 拍板）也已跑通且设计得比同类产品更懂中国家庭。但产品在**「让用户用起来」和「让更多人用起来」两端都缺关键一环**：激活端没有预置菜谱，增长端没有任何分享能力。这两个缺口把一个本可自发传播的家庭协作产品，压成了一个需要人工推广的工具。

**优先级判断：先补激活与裂变，再谈商业化。** 现在的首要目标不是赚钱，是让一个家庭能在 3 分钟内跑通首次点菜，并让这个家庭能一键把全家人拉进来。

## 二、核心优势（8 条）

### A1. 定位克制，边界守得住
- 明确声明"不是商业化点单系统"，砍掉了支付、价格、配送、评价电商化等一切诱惑。
- **为什么重要**：家庭工具的天敌是"功能臃肿"。守住边界意味着产品可以在"极简"这一体验维度上做到极致，这是相对"下厨房 + 微信群投票"这类替代方案的真实差异点。

### A2. 角色模型有洞察：掌勺人 / 干饭人
- 命名幽默、去权力化、有家庭温度，比"管理员 / 普通成员"高出一个量级。
- **身份按家庭独立**是关键设计——真实反映"我在爸妈家是干饭的，在自己家是掌勺的"这一现实。
- 两种角色数量不限（一个家庭可多个掌勺人），符合现代家庭"谁有空谁做"的真实协作方式。

### A3. 决策闭环设计到位：民主投票 → 掌勺拍板
- 很多同类产品止步于"投票汇总"，把决策难题原样抛回给用户。
- 本项目设计了 `decided` 拍板态（"今晚吃"标签 + 历史页"今晚做了"回显），**把发散的民主收敛成一次可执行决策**，符合中国家庭"征求意见、一家之主拍板"的真实决策模型。这是产品层面最值得肯定的设计。

### A4. 实时同步与一致性工程扎实
- `db.watch` 实时监听 + 300ms 去抖 + 失败 3 次退避重连 + 下拉刷新兜底。
- 乐观更新（投票/米饭）+ 服务端调和（`reconcileWithServer`），避免并发步进累积偏差。
- 跨午午夜定时器（`scheduleMidnightRefresh`）+ **业务日期以服务端 `todayList.date` 为准**，规避了客户端时间不可信导致的跨日错乱。
- 投票后卡片不重排（`mergePreservingOrder`），避免手滑点错——这是很细的体验体感。

### A5. 后端工程质量超出个人项目平均水位
- **确定性 `_id` 幂等**：`v_{date}_{familyId}_{dishId}_{openid}`、`m_{familyId}_{userId}`、`h_{voteId}`、`n_{date}_{familyId}_{dishId}`，用主键冲突天然防重，是最优雅的并发方案。
- 家庭加入用**原子条件更新**（`memberCount < 10`）做容量闸门，而非"先查后写"。
- `notify` 函数 **fail closed**（内部密钥无默认值，缺失即停用）。
- 14 个稳定 `errorCode` + 统一信封 + 前端 `ApiError` 不自动 toast（避免重复弹窗）。
- 68 项测试 + GitHub Actions 四道关卡。

### A6. 数据资产为未来留了伏笔
- `vote_history` 冗余菜名/昵称（永久可追溯）、`cookCount` 累计被点次数、`decided` 拍板标记、`rice_reports` 饭量。
- 这些数据已经足以支撑"很久没吃的菜推荐""家庭口味画像""备餐量预测"，**但目前一个都没用起来**（详见 B1）。

### A7. 视觉与微交互完成度高
- 三主题家族 + `wx.onThemeChange` 跟随系统实时联动（不重启切换），导航/tabBar/下拉底色/原生弹窗全量联动。
- 28 张定制 SVG 插画（空状态 4 + 分类占位 5 + 登录漂浮 7 + tabBar 12），且**裂图自动回退 emoji**。
- 微交互：投票成功轻震动、撤菜前中强度震动 + 二次确认、首屏骨架屏、头像降级（渐变 + 昵称首字）。
- 登录页重力感应视差（EMA 慢跟随 + 60ms 节流 + CSS 补间）——克制且有记忆点。

### A8. 零运维成本的商业模式
- 云开发免费额度内运行，无服务器、无域名、无备案，边际成本≈0。
- 对独立开发者而言，这是能长期养着的产品形态。

## 三、关键不足（10 条，按严重程度排序）

### B1. 【战略级】数据不沉淀：第 30 天和第 1 天体验完全一样
- 拍板后**没有任何结果回流**：没有"已上桌"、没有"好吃/踩雷"评价、没有"这道菜做失败了"。
- `cookCount` 只增不减（取消/撤菜/隐藏都不扣），意味着它反映的是"被点次数"而非"被做次数"，**无法区分"全家爱吃的"和"点了但从没做成的"**。
- 后果：产品没有学习曲线，用户用得越久，产品并不会越懂这个家。**长期留存的复利引擎是缺位的。**
- 这是本次评估中我最看重的一条：前面所有工程投入产生的历史数据，目前只服务于"回看"，不服务于"变好"。

### B2. 【战略级】零裂变设计：K 因子 ≈ 0
- 全代码库检索：无 `onShareAppMessage`、无 `onShareTimeline`、无 `wx.scanCode`、无 `wxacode.getUnlimited`。
- 设计文档 §3.2 明确写了"扫描家庭二维码"作为加入方式 A/B 之一，但 README「未完成功能」标注为**未实现**。规划与落地出现断裂。
- 家庭场景本是天然的 1 → N 传播场（一个人想用起来，必须把全家拉进来），这恰恰是微信生态最擅长的病毒场景。当前却只能让创建者口头报 6 位码。
- 后果：每获取一个家庭的边际成本不随规模下降，**增长曲线是线性而非指数的**。

### B3. 【战略级】冷启动内容门槛：激活漏斗最大瓶颈
- 产品价值 ≈ 菜品库规模 × 家庭活跃人数。新家庭创建后菜谱为空，掌勺人需要逐条录入（菜名 + 分类 + 可选图片）。
- 无任何预置菜谱模板、无批量导入、无"热门家常菜一键添加"。
- 判断：一个 30 道菜的家庭菜谱，手动录入约需 8–12 分钟。**大量家庭会在"录到第 5 道菜"时流失**——此时产品还没有交付任何价值（没人能点菜）。
- 这是 Aha moment（第一次看到家人点的菜出现在汇总页）之前最大的摩擦，且发生在用户投入意愿最低的时刻。

### B4. 【体验级】首屏强制点击登录，与"极短任务"场景冲突
- `app.json` 首屏固定为 `pages/login/login`，且 `login.js` 注释明确："必须由用户点击按钮确认登录"。
- 但项目用 `wx.cloud.callFunction`，**天然携带 openid、无需用户授权即可完成身份识别**（README 与 CLAUDE.md 均确认"静默登录"是设计目标，实际实现却退化成手动确认）。
- 核心场景是"饭点前 30 秒打开点个菜"的极短任务，每次冷启动（小程序被系统回收后）多一次 loading + 一次点击，是实打实的转化损耗。
- 若保留该按钮是出于隐私合规考量，则当前登录页**未见隐私协议勾选/入口**，合规收益并未拿到，体验成本却已付出——两头不落好。

### B5. 【产品级】投票无约束，决策不收敛
- `cloudfunctions/vote/index.js` 的 `addVote` 无任何票数上限校验，一人可对全部菜品投票。
- 5 口之家 × 30 道菜，理论上可产生 150 票、30 道菜全部得票。此时"拍板"退化成掌勺人凭感觉自己挑，**投票的"收敛决策"核心价值被稀释**。
- 缺少每日票数配额（如每人 3 票）或"最多点 N 道"的机制。设计文档 §3.5 未定义该约束，属于需求缺口而非实现缺陷。

### B6. 【产品级】掌勺人的高频路径比干饭人深一层
- 干饭人唯一动作"投票"：首屏一步到位。
- 掌勺人高频动作"加菜 / 隐藏今天做不了的菜 / 拍板"：菜品库藏在「我的 → 菜品库管理」二级页，隐藏菜也在二级页；menu 页只给了 FAB「+」。
- 掌勺人是**内容供给方**，其路径效率直接决定菜谱规模，进而决定整个家庭的产品价值。当前架构中，生产者的操作成本高于消费者，会抑制内容供给。

### B7. 【产品级】功能膨胀信号：「今日米饭」的投入产出比存疑
- 最新 commit 为米饭模块（`feat(rice)` + 并发安全修复），占据 menu 页首屏第二屏位（在菜品列表之上）。
- 价值判断：对掌勺人"煮多少米"有真实价值，但对主任务"决定吃什么"弱相关；且为纯手动上报（无默认值、无历史记忆、每天都要点 ±0.5 碗）。
- 风险：**把主流程往下挤、增加干饭人的认知负荷与操作负担**。干饭人本来只需"点菜就完事了"，现在多了一个必须天天填的数字。
- 建议：验证其真实使用率，考虑下沉到汇总页、折叠，或加"沿用昨天"默认值。

### B8. 【产品级】时间维度单一：只有"今天"
- 无午/晚餐区分，无"明天"预点。`dailyReset` 每日 0 点清空，决策窗口只有一天。
- 真实需求缺口：周末/节假日三餐、以及"明晚想吃啥"（需要提前备菜/解冻）在这些场景下完全无法承载。
- 设计文档把"多餐次支持"列为"未来扩展"，但从产品完整度看，这是主场景的自然延伸而非锦上添花。

### B9. 【用户级】适老化缺位，而"爸妈"是核心目标人群
- 设计文档 §1.2 核心场景明确写了"姐姐弟弟和爸妈"，即中老年用户是一等公民。
- 但全项目无大字模式、无字号调节、头像 40px、按钮与列表项偏紧凑、无语音播报、无障碍仅做到 `aria-label`。
- 给爸妈用的产品不做适老化，是真实的、可预见的流失点——而且流失的是"家庭能否全员上线"的关键成员（少一个人，投票价值就少一分）。

### B10. 【上线级】价值交付依赖人工运维，且通知能力处于停用态
- `dailyReset` 定时触发器**需在控制台手工配置 Cron**，未配置则历史页永远无数据、隐藏菜品不会自动恢复（README 已承认）。
- 订阅消息模板 ID 未配置 → 通知功能自动停用。这直接砍掉了"弟弟点了红烧肉"的异步触达，产品退化成"打开才看得到"，**实时同步的一半价值消失**。
- 合规：已支持用户自定义昵称与头像（云存储 `avatars/{openid}/`），但未见隐私协议/用户协议入口。微信审核对"收集用户信息"高度敏感，需提前准备。

## 四、优化建议（可落地，按优先级）

### P0 — 上线前必须清零（1–2 周）

| # | 问题 | 落地动作 | 验收标准 |
|:---|:---|:---|:---|
| P0-1 | 无分享裂变 | ① 各页面加 `onShareAppMessage`，生成携带 `familyId` 的家庭邀请卡片；② 云函数用 `wxacode.getUnlimited` 生成家庭小程序码，家庭管理页可展示/保存；③ 加入页支持 `wx.scanCode` 扫码 | 新成员从"收到卡片"到"进入家庭"≤2 步；分享点击率可埋点观测 |
| P0-2 | 菜谱冷启动 | 内置 50 道家常菜模板（按 5 分类，含分类占位图），创建家庭时提供"一键导入常吃的菜"勾选页 | 新家庭从创建到可点菜 ≤60 秒 |
| P0-3 | 通知停用 | 申请订阅消息模板 ID，配置环境变量 + `config.js`；在点菜/拍板关键节点埋授权引导 | 第一票能触达掌勺人 |

| P0-5 | 运维依赖 | 部署文档中把 `dailyReset` Cron 提前为"上线检查清单"第 1 项；考虑加"历史数据为空"时的引导提示 | 新环境部署不遗漏触发器 |

### P1 — 体验与留存（2–4 周）

| # | 问题 | 落地动作 | 预期收益 |
|:---|:---|:---|:---|
| P1-1 | 决策不收敛 | 引入每日票数配额（默认每人 3 票，家庭可配置 1–5），点满后按钮置灰并提示"票数用完了，取消一个再点" | 汇总页从"30 道菜"收敛到"3–8 道菜"，拍板成本大幅下降 |
| P1-2 | 冷启动摩擦 | 冷启动改为静默登录直达；若必须保留确认按钮，则加"下次自动进入"勾选并本地记忆 | 每次冷启动节省 1 次点击 + 1 次 loading |
| P1-3 | 数据不沉淀（B1） | ① 拍板后的菜加"已上桌"确认；② 次日/当餐后支持 1 星评价（好吃/一般/踩雷）；③ `cookCount` 拆为 `voteCount` 与 `cookedCount` 两个字段 | 30 天后可产出"我家 TOP10 常吃菜""好久没吃了" |
| P1-4 | 掌勺人路径 | menu 页分类栏右侧加"管理"入口（加菜/隐藏/恢复一步可达）；隐藏菜支持长按卡片直接操作 | 菜谱供给效率提升，内容规模更快起量 |
| P1-5 | 米饭模块验证 | 埋点观测使用率；若 <30% 则下沉到汇总页或折叠，并加"沿用昨天"默认值 | 释放首屏给主流程，降低干饭人操作负担 |
| P1-6 | 历史复用 | 历史页加"再来一次"——把某天的菜单一键复制为今日候选 | 降低重复决策成本，提升回访 |

### P2 — 增长与商业化（1–3 月）

| # | 方向 | 落地动作 | 商业判断 |
|:---|:---|:---|:---|
| P2-1 | 智能推荐 | 基于 `cookedCount` + 历史 + 季节，每周一推送"这周试试这几道"；"XX 天没吃红烧肉了" | 把沉淀数据变成主动价值，提升周活 |

| P2-4 | 商业化选择 | 见下节"商业化路径判断" | 需主动做选择题 |

## 五、商业化与增长潜力判断

### 5.1 天花板：诚实地说，独立 C 端变现空间有限

| 指标 | 判断 |
|:---|:---|
| 单家庭 DAU | 1–5 人（受 10 人上限约束） |
| 使用频次 | 1–2 次/天（饭点前），但单次时长 <60 秒 |
| 自然增长 | 当前 K 因子 ≈ 0；补上分享后，家庭场景可达 K > 1（一人拉全家） |
| 留存风险 | 高。纯工具型、无内容沉淀、无社交关系沉淀，7 日留存是生死线 |
| 支付方式 | 无。家庭场景向家人收费，心理阻力极大 |

### 5.2 四条可选路径（推荐度排序）

| 路径 | 说明 | 推荐度 | 理由 |
|:---|:---|:---|:---|
| **① 作品集 / 简历资产** | 已具备完整架构、测试、CI、设计体系，是极好的能力证明 | ★★★★★ | 当下最现实的"变现"，零成本、即刻生效 |
| **② AI 增值（首选商业化方向）** | 基于菜谱 + 历史 + 季节，AI 生成"一周菜单""剩菜怎么做""买菜清单" | ★★★★☆ | 与已有数据资产天然契合；订阅制可接受；不与"极简"定位冲突（可折叠） |
| **③ 转 B 端团餐 / 公司食堂** | 同样的投票+拍板模型，客户是行政/食堂承包方，付费意愿明确 | ★★★☆☆ | 模型可复用，但需重构家庭概念为"组织"，工作量不小 |
| **④ 广告 / 电商导流** |  Banner、食材带货 | ★☆☆☆☆ | **强烈不推荐**。会直接摧毁"纯净、克制"这一唯一差异点，且家庭 DAU 不支持广告变现模型 |

### 5.3 我的建议

**短期（6 个月内）不要商业化。** 优先把 P0 + P1 做完，跑出真实家庭留存数据（7 日留存、周活跃家庭数、日均投票数）。当"周活跃家庭"达到四位数时，再启动 ② AI 增值。在此之前，任何商业化尝试都会因为样本太小而无法验证，且会污染核心体验。

**一个关键提醒**：本产品最值钱的不是流量，是**"家庭口味数据"**——哪道菜在这个家最受欢迎、多久没吃了、谁不吃辣。这是外卖平台和菜谱 App 都拿不到的数据。如果未来要做商业化，这条数据线才是护城河，而不是用户量。
