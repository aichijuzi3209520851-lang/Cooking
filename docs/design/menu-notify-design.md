# 菜单提交与否决通知 — 功能设计（NOTIFY-002）

> 目标：等饭的「提交今日菜单」→ 整合成一条通知推给掌勺的；掌勺的「一票否决」→ 通知投过该菜的人并附原因。
> 状态：设计稿（待确认决策点后实现）

---

## 1. 现状盘点（已具备的能力）

| 能力 | 实现位置 | 说明 |
|:---|:---|:---|
| 角色体系 | `family_members.role` | `chef`（掌勺）/ 其他（等饭），已有 `requireChef` / `requireMember` 守卫 |
| 菜品库持久化 | `dishes` 集合 | 掌勺可增删改，**不会自动消失**（`dailyReset` 只重置 `isHidden`） |
| 投票 | `daily_votes` | 确定性 `_id` 幂等；chef 与等饭的都可投（`requireMember`） |
| **一票否决** | `vote.chefCancel` | **语义正是「今日不做」**：仅清当日该菜所有票，**菜品保留**、家人可再点 |
| 否决通知 | `notify.sendCancelNotify` | **已有**，通知投过该菜且仍是成员的用户 |
| 通知开关 | `users.notifyEnabled` + `profile` 页设置 | 用户可自行开关 |
| 防重防并发 | `notify_ledger` + `NOTIFY_INTERNAL_KEY`（fail closed） | 云函数间调用有内部密钥校验 |

**结论**：需求 ② 已实现 ~80%，仅缺「否决原因」；需求 ① 为全新。

## 2. ⚠️ 微信订阅消息的三条硬约束（决定方案形态）

### 2.1 只能用「一次性订阅」

家庭工具类小程序**不具备长期订阅资格**（长期订阅仅开放给政务、医疗、交通等特定行业）。
一次性订阅的规则是：**用户授权一次 = 只能发送一条**，发完即消耗。

影响：
- 掌勺的要收到「菜单提交通知」，必须**提前授权**；且授权一次只够收一条
- 因此必须引导用户勾选**「总是保持以上选择，不再询问」**——勾选后后续调用静默返回 `accept`，等效"长期"
- 现状 `profile` 页已有通知设置入口，复用即可

### 2.2 模板字段由微信固定，且 `thing` ≤ 20 字符

模板必须在小程序管理后台从微信提供的类目里申请，**字段名与数量不可自定义**。
`thing` 类型字段**最多 20 个字符** —— 多道菜名必须截断。

影响：
- 「整合多道菜」只能显示概要，例如：`红烧肉、青菜等 3 道菜`
- 现有 `notify.sendToOne()` **硬编码了 `thing1`/`thing2` 两个字段** →
  需改造为**数据驱动**（传 `data` 对象），否则新模板字段接不上

### 2.3 模板数量有限（个人主体通常仅 5 个）

现有已用 3 个（vote / cancel / menu）。新增需谨慎，**优先复用**：

| 新需求 | 首选方案 |
|:---|:---|
| 菜单提交通知 | **复用 `menu`（拍板）模板**，字段复用 `thing1`=菜品概要、`thing2`=提交人 |
| 否决原因 | 复用 `cancel`（撤菜）模板，但**需该模板具备第 3 个字段**（如 `thing3`）承载原因；若只有 2 个字段，则把菜名与原因合并进 `thing2`（受 20 字符限制，需精简文案） |

## 3. 功能流程（理顺后的逻辑）

```
掌勺的添加菜品 ──────────────► dishes（持久，永不自动清除）
                                    │
等饭的浏览菜品库 ────────────────► 投票（daily_votes，实时累加）
   掌勺的也可投票                     │
                                    ▼
                        等饭的点「提交今日菜单」①
                                    │
                    汇总当日全部有效投票（按菜品去重）
                                    │
                    写入 menu_submissions（幂等，可重复提交）
                                    │
                    发通知给家庭内所有 chef
                      「今日菜单已提交：红烧肉等 3 道菜 / 由 小明 提交」
                                    │
                                    ▼
                        掌勺的查看并决定
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
    决定做 → 保留投票                            今日不做 → 「一票否决」②
                                                        │
                                          选择原因（预设 5 项 / 自定义）
                                                        │
                                          清空该菜当日投票（菜品保留）
                                                        │
                                          通知投过该菜的人：
                                            「红烧肉 今日不做 · 家里没调料了」
```

## 4. 数据模型

### 4.1 新增集合 `menu_submissions`

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `_id` | string | `s_{date}_{familyId}_{openid}` —— 每人每天一条，重复提交覆盖（幂等） |
| `familyId` | string | 家庭 |
| `userId` | string | 提交人 openid |
| `userName` | string | 提交人昵称（冗余，避免通知时再查） |
| `date` | string | 业务日期（东八区，与 `daily_votes` 同口径） |
| `dishIds` | array | 本次提交汇总的菜品 ID |
| `dishCount` | number | 菜品数 |
| `createdAt` / `updatedAt` | Date | 时间戳 |

**索引**：`familyId + date`（查当日提交情况）、`userId + date`（判重）

**清理**：由 `dailyReset` 按 `date` 清理（与 `rice_reports` 同策略）

### 4.2 否决原因

不新增集合。写入 `dishes` 的当日否决记录，或在 `daily_votes` 删除前落一条 `vote_history` 备注。

**更简方案**：原因仅用于**当次通知**，不持久化（用户没要求历史可查）。
若后续要展示"今天为什么没做这道菜"，再扩展。

## 5. 接口契约

### 5.1 新增 `vote.submitMenu`

```js
// 入参：{ familyId }
// 前置：调用者必须是家庭成员
// 逻辑：
//   1. 汇总当日 daily_votes（按 dishId 去重，过滤已隐藏菜品）
//   2. 为空 → 抛 NO_VOTE_TODAY「今天还没有人点菜」
//   3. upsert menu_submissions（_id = s_{date}_{familyId}_{openid}）
//   4. 调 notify.sendMenuSubmitNotify（失败不阻塞，记日志）
// 返回：{ date, dishCount, dishNames: string[], notified: number }
```

### 5.2 扩展 `vote.chefCancel`

```js
// 入参：{ familyId, dishId, reason }   ← reason 为新增可选参数
// reason 取值：预设短语（≤20 字）或用户自定义（≤20 字，入参处截断校验）
// 逻辑：现有逻辑不变，仅把 reason 透传给 notify.sendCancelNotify
// 返回：{ familyId, dishId, affectedCount, reason }
```

### 5.3 扩展 `notify`

| action | 变化 |
|:---|:---|
| `sendMenuSubmitNotify` | **新增**。收件人 = 家庭内所有 chef；概要文案：`{首菜}等 {N} 道菜` |
| `sendCancelNotify` | 增加 `reason` 参数，写入模板第 2/3 字段 |
| `sendToOne` → `sendOne(openid, templateId, data)` | **改造为数据驱动**，不再硬编码 `thing1`/`thing2`，模板字段变化只改调用处 |

### 5.4 前端 `api.js`

```js
voteApi.submitMenu = (familyId) => call('vote', { action: 'submitMenu', familyId })
voteApi.chefCancel = (familyId, dishId, reason) =>
  call('vote', { action: 'chefCancel', familyId, dishId, reason }, true)
```

## 6. 交互设计

### 6.1 「提交今日菜单」按钮

- **位置**：汇总页（`pages/summary`）底部 —— 汇总页本身就是"今天大家点了什么"的视图，语义最贴合
- **文案**：`提交今日菜单`；已提交过则显示 `重新提交`
- **前置校验**：当日无投票 → 禁用并提示
- **二次确认**：弹确认框说明「将把今日 3 道菜提交给掌勺的」
- **提交后**：toast「已提交给掌勺的」+ 触发订阅授权请求（若未授权）

### 6.2 「一票否决」原因选择

现有 `showConfirm` 单行确认 → 改为**原因选择弹窗**：

| 预设选项 | 文案（可直接入通知） |
|:---|:---|
| 1 | 今天忘记买它了 |
| 2 | 家里没调料了 |
| 3 | 太麻烦了不想做 |
| 4 | 食材不够了 |
| 5 | 今天想吃点别的 |
| 6 | 其他（自定义，≤20 字） |

- 弹窗标题：`今天不做「红烧肉」`
- 说明文字：`选个原因，会告诉点这道菜的家人`
- 交互：点选项 → 立即否决（不再二次确认）；「其他」展开输入框

## 9. 待确认的决策点

1. **谁能提交菜单？**
   - A. 任何家庭成员（含掌勺）— *默认*
   - B. 仅等饭的（掌勺的无需提交，他直接决定）
2. **提交粒度？**
   - A. 每个成员各自提交，各自的通知 — *默认，贴合你的描述*
   - B. 全家庭共用一个「今日菜单」提交状态（谁点都算，一次提交）
3. **通知收件人（菜单提交）**
   - A. 家庭内所有 chef（通常 1 人）— *默认*
   - B. 仅提交者之外的其他成员
4. **否决原因是否要落库？**
   - A. 仅用于当次通知，不存 — *默认，轻量*
   - B. 存进 `vote_history`，历史页可回看「那天为什么没做这道菜」
5. **掌勺的一票否决后，菜品状态**
   - 现状：**菜品保留**（仅清当日票）— 符合你的描述，保持不变 ✅
