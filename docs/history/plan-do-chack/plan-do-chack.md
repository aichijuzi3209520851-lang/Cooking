## 2. 项目范围

项目路径：D:/we-chat/project/miniprogram-11

项目类型：微信小程序原生开发 + CloudBase 云函数 + CloudBase NoSQL + 云存储 + 定时触发器。

主要业务：家庭创建与加入、家庭成员角色、菜品库、每日点菜、点菜汇总、历史归档、主题设置、订阅消息。

当前目标：将项目从开发中的功能原型提升到可测试、可审查、可持续发布的 MVP 版本。

## 3. 执行原则

1. 先修复核心业务闭环，再做视觉和非关键体验优化。
2. 所有权限、归属、角色、计数和状态流转必须在云函数服务端校验，不能信任客户端传入的用户身份字段。
3. 所有跨集合写操作都必须考虑事务、幂等、失败重试和部分成功。
4. 不得通过兼容多个不明确的数据格式来掩盖接口契约问题。接口要有唯一、明确、可测试的返回结构。
5. 不得添加硬编码密钥、模板 ID、环境密钥或其他敏感信息。
6. 不得使用全量读取、无限制 setData、无界面 loading 或静默吞错来掩盖性能和稳定性问题。
7. 不得执行生产环境部署、数据库批量删除、数据库权限变更或清空数据等破坏性操作，除非用户明确批准。
8. 保留当前工作区中已有的用户改动，不使用 git reset --hard、git checkout -- 或其他覆盖性命令。
9. 修改范围要围绕本文件需求，不进行无关重构。
10. 如果 CloudBase SDK 的某个能力需要控制台配置或当前依赖版本不支持，必须在结果验收.md 中明确标记为 BLOCKED，并写出人工操作步骤，不能假装已经完成。

## 5. P0：必须先完成的核心修复

### API-001：统一今日投票接口契约

现状：

- cloudfunctions/vote/index.js 的 todayList 返回 { date, groups }；
- miniprogram/pages/menu/menu.js 读取 voteData.list；
- miniprogram/pages/summary/summary.js 读取 voteData.list；
- 前端因此无法使用后端返回的投票分组。

要求：

1. 确定唯一返回结构，推荐保留后端已有的 groups 结构：

   - date：服务端计算的 YYYY-MM-DD；
   - groups：数组；
   - 每个 group 至少包含 dishId、dishName 或统一后的 name、category、imageUrl、isHidden、voters；
   - 每个 voter 至少包含 openid 或替代性的稳定成员标识、nickname、avatarUrl、votedAt。

2. 菜单页必须从 voteData.groups 读取数据。
3. 汇总页必须从 voteData.groups 读取数据。
4. 明确 group 的菜品字段名称。推荐统一使用 dishId 作为业务 ID，禁止同一 DTO 同时依赖 dishId 和 _id。
5. 菜品对象和投票分组对象可以有不同字段，但必须在数据转换层完成映射，不能让 WXML 自己猜字段。
6. 删除 Array.isArray、list、groups 等多套猜测式兼容逻辑，改成单一契约并在异常时给出明确错误。
7. 在 api.js 或独立的 DTO 转换模块中补充最小的数据结构校验。
8. API 错误返回要包含稳定的 errorCode 和 message，前端根据 errorCode 决定提示，不要只依赖中文文案。

验收：

- 一个用户投票后重新进入菜单页，投票状态仍然存在；
- 两个菜品分别被投票时，两个菜品的 voters 映射正确；
- 汇总页显示菜名、投票人数和投票成员；
- 汇总页的撤菜按钮传入真实 dishId；
- 无投票时 groups 为空数组，页面显示正确空状态；
- 删除或隐藏菜品后的异常数据不会导致页面崩溃。

### API-002：修复菜单和汇总的 ID 映射

要求：

1. menu.js 使用 dish._id 与投票 group.dishId 建立映射。
2. votesMap 的 key 必须是 dishId，而不是依赖不存在的 group._id。
3. summary.js 生成的列表项必须保留 dishId。
4. summary.wxml 的撤菜按钮必须传 data-id={{item.dishId}} 或统一后的字段。
5. dish-card 只接收已经转换好的 voters，不在组件中猜测后端字段。
6. 为缺失菜品、已隐藏菜品、已删除菜品保留明确的展示策略，不得出现 undefined 作为 key 或请求参数。

### UI-001：修复隐藏菜品的管理闭环

要求：

1. 菜品管理列表支持 includeHidden 参数。
2. 普通菜单默认只能获取 isHidden=false 的菜品。
3. chef 菜品管理页可以看到隐藏菜品，并显示“显示菜品”操作。
4. 服务端必须校验 includeHidden 只能由 chef 使用，不能让客户端任意读取其他家庭数据。
5. 隐藏菜品时清理当日投票，并确保客户端最终状态一致。
6. 恢复菜品时只更新 isHidden，不得重复创建菜品。
7. chefCancel、toggleHidden、deleteDish 的当日投票清理逻辑必须统一，避免三个接口产生不同的计数和通知行为。
8. 菜品隐藏状态变化不能只依赖 daily_votes watcher 才能刷新。应监听菜品状态或在操作成功后让其他页面有可靠的刷新机制。

验收：

- chef 隐藏菜品后，普通成员看不到；
- chef 重新打开菜品库后能看到该隐藏菜品；
- chef 点击显示后，普通成员可以重新看到；
- 隐藏零投票菜品时，其他设备也能刷新状态；
- 隐藏、撤菜、删除操作不会留下当日可见投票。

### DATA-001：家庭操作的原子性、幂等和生命周期

重点检查文件：cloudfunctions/family/index.js。

要求：

1. 创建家庭的家庭记录、成员记录、用户 currentFamilyId 更新必须使用 CloudBase 当前 SDK 支持的事务能力，或设计可靠的补偿机制。
2. 加入家庭必须防止并发超员。不能只执行“先查人数，再 add，再 inc”这一组非原子操作。
3. family_members 必须建立 familyId + userId 的唯一约束。若控制台不能通过代码创建索引，至少新增部署文档和验证脚本，并在结果报告中标出控制台步骤。
4. 重复加入必须幂等：已加入时只能切换当前家庭，不得重复创建成员记录或增加 memberCount。
5. 加入流程任一步骤失败时，不得留下成员记录、错误 memberCount 或错误 currentFamilyId。
6. 移除成员和退出家庭必须保证成员关系、当日投票、memberCount、用户当前家庭状态的一致性。
7. 保留当前产品文档的规则：最后一名成员退出时自动解散家庭并清理关联数据。
8. creator 不是最后一名成员时不得直接退出，必须提示先转移创建者身份或由产品明确支持所有权转移。
9. 最后成员退出的清理范围至少包括 families、family_members、dishes、daily_votes、vote_history 的家庭数据；云存储图片需要单独清理或记录待清理任务。
10. 清理操作必须可重复执行，不能因为重复请求而报错或产生负数计数。

验收：

- 两个账号并发加入人数为 9 的家庭，最终成员数不超过 10；
- 同一账号快速重复加入，不产生重复成员；
- 家庭创建中间步骤失败后没有孤儿家庭；
- 创建者不是最后一人时退出被拒绝；
- 最后一人退出后家庭数据和菜单数据按规则清理；
- 被移除成员无法继续读取或写入原家庭数据。

### DATA-002：投票写入和计数一致性

要求：

1. 使用确定性 daily_votes ID 或唯一索引确保同一用户、同一家庭、同一菜品、同一天只有一票。
2. 重复请求必须返回稳定的业务错误码，例如 VOTE_ALREADY_EXISTS。
3. 投票记录写入和派生计数更新必须使用事务，或提供明确的补偿/修复机制。
4. 明确 cookCount 的语义。按照设计文档，推荐将 cookCount 定义为累计被点次数：

   - 新增一票成功后加一；
   - 取消自己的票不减少累计值；
   - chef 撤菜、隐藏、删除和成员退出不减少累计值；
   - 当日当前投票数通过 daily_votes 聚合得到。

5. 如果产品实际需要的是当前票数，必须将字段重命名为清晰的 currentVoteCount，并修改所有排序、归档和清理逻辑，不能继续混用 cookCount。
6. 不允许出现负数计数。
7. 点菜、取消、撤菜同时发生时，最终 daily_votes 和页面统计必须一致。
8. 发送通知失败不能回滚已经成功的投票，但必须记录失败日志或任务状态。

验收：

- 双击或并发点菜只生成一条投票；
- 点菜失败时不会残留一条客户端不知道的投票；
- 取消后当日投票消失，累计统计符合约定；
- chef 撤菜后当日投票清理，历史累计字段不出现错误扣减；
- 跨家庭传入 dishId、familyId 组合会被拒绝。

### DATA-003：dailyReset 可重试、可恢复、可观察

重点检查文件：cloudfunctions/dailyReset/index.js。

要求：

1. vote_history 写入必须幂等。推荐使用 daily_votes 原始 _id 派生固定历史 ID，或者使用 upsert。
2. 定时任务重复执行不能产生重复历史记录。
3. 归档和删除分批处理，不能将全部数据无限制加载到内存。优先使用游标或稳定排序分页，不使用大数据量 skip。
4. 单个批次失败时要保留可重试状态，并记录处理日期、批次范围、成功数量、失败数量。
5. 删除 daily_votes 前必须确保对应历史已经幂等写入成功。
6. 任务需要有明确的执行日志，至少包含 jobId、业务日期、开始时间、结束时间、处理数量、失败原因。
7. 核对定时触发器配置和实际 CloudBase cron 格式，确保每日东八区 00:00 的业务目标成立。
8. 增加手动测试入口或受保护的测试方式，仅允许开发环境使用，不能给普通客户端留下任意触发入口。
9. 验证 isHidden 重置不会覆盖其他正在执行的菜品管理更新。

验收：

- 第一次运行可以完成归档；
- 运行到一半失败后再次运行不会重复历史；
- 空数据运行成功且不报错；
- 大于一个批次的数据可以完整处理；
- 任务执行结果能在日志或结果中定位。

## 6. P0：数据库权限、索引和存储安全

### SEC-001：建立可审查的数据库权限设计

当前设计依赖数据库权限，但仓库没有规则文件，必须补齐可审查的安全设计。

要求：

1. 为 users、families、family_members、dishes、daily_votes、vote_history 分别记录读、创建、更新、删除权限。
2. 明确哪些操作只能由云函数执行。
3. daily_votes 的客户端 watch 必须经过最小权限验证。不能因为需要实时监听就把 daily_votes 设置为全量公开可读。
4. 如果 CloudBase 规则无法安全表达“家庭成员可读”，不得继续直接暴露 raw daily_votes；应改为云函数返回的安全读模型、成员 ID 列表或其他可验证方案。
5. 规则配置必须说明 auth.openid、文档字段和跨家庭隔离关系。
6. 增加跨家庭读取、非成员读取、eater 写入、eater 撤菜、伪造 userId 等负向测试。
7. 增加数据库索引清单，至少覆盖：

   - family_members：familyId + userId；
   - daily_votes：familyId + dishId + userId + date；
   - daily_votes：familyId + date；
   - dishes：familyId + isHidden + category；
   - dishes：familyId + cookCount + createdAt；
   - vote_history：familyId + date + createdAt；
   - families：joinCode 唯一约束。

8. 如果规则和索引只能在控制台配置，新增 docs/deployment/database.md，写明配置项、截图或验证命令，并在结果验收中标记“代码完成、控制台待确认”。

### SEC-002：内部 notify 调用安全

要求：

1. 删除源码中的默认内部密钥。
2. 生产环境必须从环境变量读取密钥，缺失时 fail closed。
3. notify 必须验证 action 所需的 familyId、dishId、affectedUserIds 关系，不能只凭内部密钥向任意用户发送通知。
4. 客户端不能直接调用 notify 成功。
5. 不在日志中打印密钥、完整 event、完整环境变量或完整用户列表。

### STORAGE-001：图片上传和生命周期

要求：

1. 校验文件大小、扩展名和 MIME 类型，不能只相信客户端选择器。
2. imageUrl 只能接受当前家庭允许的 CloudBase 文件标识或受控 URL。
3. 文件路径必须包含合法家庭 ID，并且不能让普通成员向其他家庭路径任意写入。
4. 菜品替换图片时，保存成功后清理旧图片。
5. 菜品删除时清理关联图片，或建立异步清理任务。
6. 图片上传成功但菜品保存失败时，删除新上传文件，避免产生孤儿文件。
7. 在 README 或部署文档中写明云存储读写权限和正式环境安全域名配置。

## 7. P1：登录、路由和状态管理

### AUTH-001：增加登录准备态

要求：

1. app.js 暴露可等待的登录初始化 Promise 或等价的 ready 状态。
2. 菜单、汇总、个人中心和需要家庭数据的页面，在登录未完成前不能根据空的 globalData 做最终路由决策。
3. 登录成功后统一刷新当前家庭、角色、用户信息和家庭列表。
4. 登录失败必须有用户可触发的重试入口，不得只 console.error。
5. 登录成功回调必须真正被页面使用，不能保留未接入的 loginCallback 变量。
6. 缓存只能作为首屏临时数据，服务端登录结果必须覆盖缓存；发现 currentFamilyId 已失效时要自动修正。
7. 登录云函数不要把所有数据库异常都当成“用户不存在”。需要区分 not found、权限错误、网络错误和真正的创建冲突。

### AUTH-002：用户资料和家庭信息一致

要求：

1. login 返回当前家庭管理页所需的 joinCode、memberCount、creatorId 等字段，或在进入管理页时通过 family.list 重新加载。
2. family.list 和 login 返回的家庭 DTO 字段统一，不能一个使用 _id、另一个使用 familyId。
3. 若产品需要昵称和头像，提供用户主动授权的资料完善流程，不得静默调用受隐私限制的 API。
4. 若暂时不实现用户资料授权，应统一使用默认昵称并同步修改文档，不得宣称已经获取微信昵称和头像。

### TIME-001：统一业务日期

要求：

1. 今日日期以服务端返回的 date 为准。
2. 页面 onShow 时重新计算日期，不长期使用 onLoad 时的旧日期。
3. 页面跨午夜时要关闭旧 watcher、重新建立新日期 watcher 并重新加载数据。
4. 页面展示日期、投票写入日期和 dailyReset 日期必须采用同一东八区规则。
5. 增加设备时区、设备时间异常和跨午夜的测试说明。

## 8. P1：实时同步、性能和错误处理

### SYNC-001：控制实时监听成本

要求：

1. watcher 只监听当前家庭、当前业务日期和必要字段。
2. 监听回调不能每次都无条件重载全部菜品和全部投票。至少要根据 docChanges 判断新增、删除和更新，或者明确说明为什么采用重新拉取，并控制请求去重。
3. 同一页面同一时间只能有一个 watcher 和一个 load 请求。
4. watcher 出错后需要有限次数重连或提供下拉刷新兜底，不能永久静默失效。
5. 页面隐藏和卸载时必须关闭 watcher，切换家庭时必须关闭旧 watcher。
6. 不向 setData 传递不需要展示的完整用户对象、内部字段和重复数据。

### PERF-001：分页、查询和数据量

要求：

1. 菜单页不能请求 200 条再依赖后端截断。统一使用真实分页或明确的家庭菜品数量上限。
2. 菜品列表的 page、pageSize、category 必须在服务端做类型和范围校验。
3. 避免大 offset skip，数据量增长后使用稳定游标分页。
4. login、family.list、成员列表等联查优先批量查询或 Promise.all，避免可扩展路径上的串行 N+1。
5. 每个列表页面必须有 loading、空数据、加载失败、重试和没有更多数据状态。
6. 加入简单的性能观测：请求耗时、返回数量、watcher 重载次数、setData 数据量或等价指标。

### ERROR-001：统一错误处理

要求：

1. api.js 不要同时自动 toast、页面再次 toast，避免重复提示。
2. 云函数返回稳定的 errorCode、message 和必要的可观测字段。
3. 前端根据错误类型区分权限失败、网络失败、重复操作、数据不存在和服务异常。
4. 失败状态必须允许用户重试，不能只显示一次 toast 后页面保持半成品状态。
5. 日志中不能包含内部密钥、完整 openid 列表和敏感用户数据。

## 9. P1：订阅通知

### NOTIFY-001：完成真实通知链路

要求：

1. 使用正式的订阅消息模板 ID 配置，不把模板 ID 写死在业务代码中。
2. 用户首次点菜或进入通知设置时，调用 wx.requestSubscribeMessage，并正确处理拒绝、部分同意和过期状态。
3. 用户的通知状态不能只用一个默认 true 表示，应记录授权结果和最近失败原因。
4. 点菜通知只发送给当前家庭 chef。
5. 撤菜通知只发送给确实投过该菜的当前家庭成员。
6. 发送通知前再次校验家庭、菜品和用户关系。
7. 通知失败不影响投票主流程，但需要可观测、可重试或可人工排查。
8. 跳转页面必须是实际可用的页面，不能固定跳转 welcome 后让用户重新操作。
9. 对“第一票通知”的并发竞态进行测试，不能依赖 count 结果恰好等于 1 作为唯一保证。

## 10. P2：资源、文档和产品一致性

### ASSET-001：补齐分类占位图

### DOC-001：同步产品、接口和部署文档

6. README 中的安全设计必须与实际数据库规则、存储权限和内部调用机制一致。

## 13. 完成标准

只有满足以下条件，才能在结果验收.md 中将项目标记为“可进入 MVP 验收”：

- P0 问题全部 PASS；
- 核心菜单、投票、汇总、撤菜、隐藏恢复流程在两个账号或两个设备上验证通过；
- 数据库权限和索引已经验证，或明确标记为控制台阻塞项；
- dailyReset 可以重复运行而不重复历史；
- 没有硬编码密钥和占位模板 ID；
- 自动化语法检查、契约测试和核心单元测试通过；
- 结果验收.md 给出每个需求编号的证据和剩余风险。

只有满足以下条件，才能标记为“可发布”：

- P0、P1 全部 PASS；
- 真机测试通过；
- 订阅消息、云存储、数据库权限、定时触发器均在正式环境验证；
- 有可回滚版本和发布记录；
- 有隐私协议、用户资料授权说明和小程序审核所需配置；
- 有线上错误监控和定时任务失败告警。

## 14. 结果验收.md 格式要求

结果验收.md 至少包含以下章节：

1. 执行摘要；
2. 修改文件清单；
3. 按需求编号的完成状态表；
4. 自动化测试命令和输出摘要；
5. 手工测试矩阵；
6. 数据库、存储、定时任务的控制台配置状态；
7. 已知问题和剩余风险；
8. 是否建议进入 MVP 验收；
9. 是否建议发布。

状态只能使用：PASS、PARTIAL、FAIL、BLOCKED、NOT_RUN。

对 BLOCKED 和 NOT_RUN 项，必须说明原因、影响、负责人或人工下一步，不能把它们统计为完成。
